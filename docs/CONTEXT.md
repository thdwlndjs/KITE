# KITE 첫 번째 검증 루프 설계

## 1. 현재 상태 확인

KITE 프로젝트 폴더(로컬)에는 아직 코드나 실행 자산이 전혀 없다. 존재하는 것은 기획 노트 한 건뿐이며, 그 안의 근거들(Startup Genome, A/B 테스트 Peeking 문제, Say/Do Gap 등)은 전부 일반 스타트업 문헌에서 가져온 2차 자료이지, KITE가 실제로 타겟하는 세그먼트(AI로 빠르게 무언가 만드는 1인 창업자·솔로 빌더)에게서 직접 확인한 1차 증거는 없다.

즉 지금 KITE는 기능 설계 이전 단계가 아니라, **가설 검증 이전 단계**다.

## 2. 가장 위험한 가정 — 단일 문장이 아니라 underlying problem으로 정의

가장 위험한 가정을 "1인 빌더는 검증 없이 만들어서 실패하는 문제를 아프게 느낀다"는 하나의 문장으로 고정하지 않는다. 실제 사용자는 동일한 underlying problem을 서로 다른 표현과 행동으로 드러낸다 — 어떤 사람은 "만들었는데 아무도 안 썼다"는 회고로, 어떤 사람은 "다음엔 진짜 물어보고 만들 것"이라는 다짐으로, 어떤 사람은 아예 언급하지 않고 조용히 피벗하는 행동으로만 나타날 수 있다. 하나의 표현만 찾으면 실제로는 존재하는 문제를 "증거 없음"으로 잘못 판단할 위험이 크다.

따라서 가장 위험한 가정은 다음과 같이 다시 정의한다.

> **"만들기 전에 수요를 확인하지 않아서 발생하는 낭비(시간·자금·기회)"라는 underlying problem이, KITE가 상정한 세그먼트(1인 AI 빌더·솔로 창업자)에서 실제로 존재하고, 그들이 이를 인지하며, 현재 방식으로는 충분히 해결되지 않고 있다.**

이 가정은 Importance × Evidence 매트릭스에서 여전히 "지금 당장 검증" 칸에 단독으로 위치한다 — 이게 틀리면 이후 어떤 기능·카피·가격을 설계해도 무의미하기 때문이다. 이는 프로젝트 지침 6장의 "KITE 자체도 하나의 가설이다"라는 원칙과 일치한다.

## 3. 판단해야 할 6개 축

이 underlying problem을 하나의 예/아니오가 아니라 6개의 독립적인 축으로 나누어 각각 근거를 모은다. 각 축은 서로 다른 종류의 신호를 요구하며, 하나가 강하다고 다른 것도 강하다고 넘겨짚지 않는다.

| # | 축 | 확인하려는 것 | 웹검색·커뮤니티 관찰(CLAUDE.md 1~2단계, 간접 증거)만으로 확인 가능한가 |
|---|---|---|---|
| 1 | 존재 여부 | 이 문제가 실제로 발생하는가 | 가능 — 서로 다른 표현의 회고·경험담으로 확인 |
| 2 | 빈도 | 얼마나 자주 발생하는가, 우연한 사례가 아닌가 | 가능 — 반복 등장 여부로 추정 |
| 3 | 심각도 | 얼마나 아프게 느끼는가 (감정 강도, 구체적 비용/시간 손실 언급) | 가능 — 표현의 강도와 구체성으로 추정 |
| 4 | 현재 대응 방식 | 지금은 이 문제를 어떻게 해결하려 하는가 (직접 인터뷰, 그냥 만들고 봄, 커뮤니티에 물어봄 등) | 가능 — 행동 언급으로 확인 |
| 5 | 기존 방식에 대한 불만 | 현재 대응 방식에 불만이 있는가, 갭이 있는가 | 가능 — 불만·아쉬움 표현으로 확인 |
| 6 | KITE식 접근에 대한 행동 의향 | KITE가 제안하는 방식(만들기 전 시장 검증)에 실제로 행동할 의향이 있는가 | **제한적** — 관찰만으로는 직접 답을 얻을 수 없다. 이 세그먼트가 이미 존재하는 유사 도구(리뷰 마이닝 툴, 랜딩페이지 테스트 서비스, "아이디어 검증해줘" 류 GPT 등)를 실제로 찾고 쓰고 있다는 흔적을 **추론(추정 증거)**으로만 수집한다. 진짜 답은 인터뷰(CLAUDE.md 3단계) 이후에나 얻을 수 있다는 점을 명시적으로 표시한다 |

6번 축은 이번 루프에서 "검증됨"으로 표시하지 않는다 — 관찰만으로는 구조적으로 약한 신호만 얻을 수 있기 때문이다. 이는 판단 카드에도 명확히 라벨링한다.

## 4. 탐색 방법

**표현 다양화** — 축 1~5 각각에 대해 하나의 키워드가 아니라 여러 표현 클러스터를 준비한다. 예: 존재/빈도/심각도 축에는 "만들었는데 아무도 안 씀", "몇 달 갈아넣고 접었다", "돈만 날렸다", "고객 인터뷰 없이 만든 게 실수였다" 등. 현재 대응 방식/불만 축에는 "MVP 만들기 전에 뭘 확인해야 하나요", "검증 어떻게 하세요", "설문 돌렸는데 의미 없었다" 등. 이 클러스터는 탐색을 진행하면서 실제로 발견되는 표현을 반영해 계속 갱신한다.

**소스 다양화** — 서로 다른 성격의 소스 최소 2~3곳(예: 일반 웹검색, 국내 메이커·창업 커뮤니티(OKKY, 디시 스타트업 갤러리 등), 해외 메이커 커뮤니티(Indie Hackers 등))에서 수집한다. 레딧 API 폐지로 여러 검증 도구가 동시에 타격을 입은 사례가 기획 노트에 이미 기록되어 있으므로, 단일 소스 의존 금지는 처음부터 필수 조건이다.

**품질 필터 — 근접 1차 신호만 인정** — 단순히 "검증이 중요하다"는 콘텐츠, 일반적인 스타트업 조언 글, 다른 검증 도구의 마케팅 콘텐츠는 증거로 취급하지 않는다. 실제 솔로 빌더가 1인칭으로 자신의 구체적 경험(프로젝트 내용, 기간, 손실 규모 등 구체적 디테일 포함)을 이야기한 경우만 근접 1차 신호로 인정한다. 이 기준에 못 미치는 콘텐츠는 발견하더라도 증거로 집계하지 않고 별도로만 남겨 둔다(맥락 참고용).

**출처 기록** — 채택된 신호는 각각 출처 링크, 원문 인용, 날짜, 매칭된 축(1~6), 태그(추적가능/추론/가정)와 함께 저장한다.

**판단 전 최소 관찰 기준** — 판단하기 전에 미리 기준을 정해둔다. 예: 서로 다른 소스 3곳 이상, 근접 1차 신호 총 15~20건 이상. 추가로 6개 축 중 최소 한 축이라도 근거가 0건이면 그 축은 "미확인"으로 표시하고 억지로 판단하지 않는다. 기준에 도달하기 전까지는 어떤 결과가 나오더라도 "잠정 신호"로만 취급하며, 특히 초반에 나온 좋아 보이는 사례일수록 우연일 가능성을 먼저 의심한다.

## 5. 판단 프레임 — 4가지 결론

수집이 최소 관찰 기준에 도달하면, 6개 축의 패턴을 근거로 다음 네 가지 중 하나로 판단한다. 이 판단은 보고서가 아니라 다음 행동을 결정하는 카드로 출력한다.

**문제 있음** — 존재(축1)가 서로 다른 표현으로 반복 확인되고, 빈도(축2)가 우연이 아닌 수준이며, 심각도(축3)가 높다(감정적 강도, 구체적 시간·비용 손실 언급). 이 경우 축4·5(현재 대응 방식과 그 불만)를 다음 단계 포지셔닝의 힌트로 활용한다.

**문제 약함** — 존재는 확인되지만 빈도가 낮거나(간헐적 언급) 심각도가 낮다(가볍게 스쳐 지나가는 언급, 구체적 손실 언급 없음). 문제가 아예 없는 것은 아니지만 사업을 지탱할 만큼 아프지 않을 가능성이 있다.

**다른 문제가 더 큼** — 탐색 과정에서 이 세그먼트가 반복적이고 강하게 이야기하는 pain point는 확인되지만, 그것이 "검증 부재"가 아니라 인접한 다른 문제(예: 마케팅·고객 확보, 기술 실행 속도, 자금, 시간 부족, 팀 부재)로 나타난다. 이 경우 KITE가 겨냥할 문제 정의 자체를 재검토해야 한다.

**세그먼트가 잘못됨** — "검증 부재로 인한 실패"라는 문제 자체는 어딘가에서 강하게 확인되지만, KITE가 상정한 세그먼트(1인 AI 빌더·솔로 창업자)가 아니라 다른 집단(예: 이미 투자받은 스타트업, 사내 신사업 조직, 에이전시)에서 주로 나타난다. 이 경우 타겟 재정의가 필요하다.

## 6. 이번 MVP에서 의도적으로 만들지 않는 것

인터뷰 스크립트 자동 생성기, fake door 랜딩페이지, SNS 콘텐츠 자동 생성·게시, 결제·대기자 등록 기능, 여러 프로젝트를 동시에 관리하는 대시보드, 관리자 화면, 합성 페르소나 시뮬레이션은 모두 이번 루프에 필요하지 않다. Evidence Ladder 6단계 도구를 미리 다 갖추지 않는다는 원칙대로, 이들은 다음 가정에서 실제로 필요해질 때 그때 추가한다.

## 7. 다음 가설로의 연결

이 루프의 결과(4가지 판단 중 하나)는 다음 가설을 결정하는 입력이 된다.

- 문제 있음 → 다음 루프는 특정 포지셔닝(예: "만들기 전 며칠 안에 수요를 검증해준다")을 제시했을 때 실제로 반응하는지 확인하는 인터뷰(CLAUDE.md 3단계)로 진행한다. 이때 축4·5에서 확인한 현재 대응 방식과 불만이 인터뷰 질문 설계와 포지셔닝 문구의 근거가 된다.
- 문제 약함 → 세그먼트나 표현 클러스터를 좁히거나 바꿔 재탐색(포지셔닝 재작업)한다.
- 다른 문제가 더 큼 → 탐색 중 발견된 더 큰 문제를 새로운 후보 가정으로 등록하고, 그것이 KITE가 다룰 만한 문제인지부터 다시 판단한다.
- 세그먼트가 잘못됨 → 탐색 중 문제가 강하게 나타난 실제 집단을 새로운 후보 세그먼트로 등록하고 재탐색한다.

축6(KITE식 접근에 대한 행동 의향)은 이번 루프에서 강한 신호로 확정되지 않으므로, 위 네 가지 결과와 무관하게 다음 루프(인터뷰 또는 이후 fake door)에서 별도로 직접 확인해야 할 항목으로 항상 이월된다.

## 8. 다음 구현 단계 (설계 — 코드 아님)

다음으로 넘어갈 때 만들 최소 시스템의 구조는 다음과 같다.

**입력 스키마** — underlying problem 정의, 타겟 세그먼트 정의, 축1~6별 키워드 클러스터(초기값은 이 문서 4장 예시로 시작하고 탐색하면서 갱신), 최소 관찰 기준값(소스 수, 신호 건수).

**수집 실행** — 소스별로 독립된 검색 모듈을 둔다(웹검색 1개 + 커뮤니티 소스 2개로 시작). 하나의 소스가 막히거나 정책이 바뀌어도 나머지 소스로 루프가 멈추지 않도록 각 모듈을 독립적으로 실패할 수 있게 설계한다. 각 결과는 원문 URL, 발췌 인용, 날짜, 소스명, 매칭된 축, 태그(추적가능/추론/가정)를 함께 저장한다.

**품질 필터** — 근접 1차 신호 판별 기준(1인칭 서술 + 구체적 디테일 존재 여부)을 적용해 일반 조언성 콘텐츠를 걸러낸다. 자동 필터의 오탐 위험이 아직 검증되지 않았으므로 첫 버전에서는 자동 필터로 후보를 추리고 최종 채택 여부는 사람이 확인하는 방식을 병행한다.

**진행 현황 추적** — 소스 수, 총 신호 건수, 축별 커버리지, 최소 기준 대비 진행률을 보여주는 최소한의 상태 뷰. 기준 미달 시에는 판단을 내리지 않고 "탐색 계속" 상태를 유지한다.

**판단 카드 출력** — 기준 도달 시 축1~6 요약, 4가지 판단 카테고리 중 하나, 핵심 근거 인용·링크, 다음 액션 추천을 하나의 카드로 생성한다.

다음 단계는 실제 스캐폴딩(입력 스키마 정의, 소스 모듈 선정, 저장 형식 확정)이며, 착수 전 이 구조에 대한 검토가 필요하다.
